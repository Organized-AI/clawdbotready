⚡ Gateway (The Daemon)
What it is
Single long-lived process that owns everything. WebSocket server on 127.0.0.1:18789. One per host. All clients, nodes, and channels connect here.
Protocol
JSON over WebSocket. First frame must be connect. Then req/res + server-push events. Idempotency keys for side effects.

🤖 Agent Runtime
Core loop
Message → context assembly → model inference → tool execution → streaming reply → persist. Serialized per session.

Skills
Loaded from: bundled → ~/.openclaw/skills → <workspace>/skills. Each is a folder with SKILL.md (YAML frontmatter + instructions). Agent reads on demand.
Sessions
JSONL transcripts at ~/.openclaw/agents/<id>/sessions/. Queue modes: steer, followup, collect.
🧠 Context & Memory
Context = everything the model sees
System prompt + conversation history + tool results + attachments. Bounded by model's context window.
Compaction
When window fills up → summarize older messages → keep recent ones. Pre-compaction memory flush writes durable notes to disk before summarizing.
Session Pruning
Trims old tool results in-memory (doesn't rewrite transcript). Separate from compaction.
Memory
Plain Markdown on disk. MEMORY.md (curated long-term) + memory/YYYY-MM-DD.md (daily log). Vector search via embeddings (local or remote). Hybrid BM25 + vector for retrieval.
Context rot = tool results filling the window → compaction summarizes away important details → agent "forgets." This is where Apify's pre-fetched data patterns help — keep tool output small and structured.

Key point
Gateway owns all channel connections. Agent sends via message tool. Cron/heartbeat can deliver to any channel. This is what makes OpenClaw feel like "your phone is an AI."
⏰ Automation Layer
Heartbeat
Periodic agent turns in main session (default 30min). Reads HEARTBEAT.md checklist. Replies HEARTBEAT_OK if nothing to report. Delivers alerts to configured channel.
Cron
Persistent scheduled jobs. Two modes: main session (system event → next heartbeat) or isolated (fresh session, no carry-over). Delivery to any channel. Model/thinking overrides per job.
Hooks
Event-driven scripts: agent:bootstrap, before_tool_call, message_received, etc. Plugins can intercept the full lifecycle.
Webhooks
HTTP endpoint that triggers agent turns from external services.

Where Apify plugs in: Tool Execution phase. Skills teach the agent when/how to call Apify actors via exec (CLI) or direct API calls. Results come back as tool output → enter context window. The smaller and more structured the output, the less context rot.
🔌 Apify × OpenClaw Integration Points
Pattern 1: Skills (Agent-Initiated)
How
SKILL.md teaches agent to call Apify actors when relevant. Agent decides when to invoke. Runs via exec tool (Apify CLI or curl).
Good for
On-demand scraping, lead gen, competitor research. Agent autonomously decides "I need web data" and calls the right actor.
Context cost
⚠️ Each tool result enters context. Need structured, minimal output.
Pattern 2: Cron + Pre-fetch (Scheduled)
How
Cron job triggers Apify actor on schedule → results stored in Apify dataset or local file. Agent reads pre-fetched data, never scrapes live.
Good for
Morning briefings, price monitoring, social listening. Separates collection from interaction.
Context cost
✅ Minimal — agent reads a summary file, not raw scrape output.
Pattern 3: Webhook → Agent Turn
How
Apify actor completes → webhook hits OpenClaw → triggers isolated agent turn with results. Agent processes and delivers to channel.
Good for
Event-driven alerts. Price drops, new mentions, content changes. Push instead of poll.
Context cost
✅ Isolated session — no main context pollution.
Pattern 4: mcpc / MCP (Direct Tool)
How
Agent calls Apify actors as MCP tools. Each tool result returns to context.
Good for
Quick lookups, single-actor calls. Not great for chains.
Context cost
⚠️ Every result = ~400+ tokens. Chains compound fast. This is the context rot problem.
